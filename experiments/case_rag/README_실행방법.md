# DataGuard · Case-Based RAG 독립 A/B 실험 v0.1

## 무엇을 하는 프로그램인가?

기존 `data-guard-agent`(①~⑤)를 **수정하지 않고**, Qwen2.5 7B의 `보완 후` 수정 지시를 두 방식으로 비교합니다.

- **A / Baseline**: 현재 검사 오류 + 현재 구문규칙만 로컬 Ollama에 전달
- **B / Case RAG**: 현재 검사 오류 + 현재 구문규칙 + Case KB 검색 사례를 로컬 Ollama에 전달
- **평가**: 각각의 실제 모델 제안과 Ground Truth(비교용)를 담당자가 대조하여 `적절 / 부적절 / 추가 검토 필요` 기록
- **저장**: 별도 CSV + `테스트 결과`, `비고` 시트를 포함한 Excel. 실제 원본 파일을 변경하지 않음.

현재 검색은 **SQLite + 구조화/키워드 유사도**를 사용합니다. 아직 임베딩·벡터 DB·GraphRAG·LangGraph를 붙이지 않았습니다. `검색 관련도 점수`는 정확도가 아니라 검색 순서용 점수입니다.

## Windows 실행 방법

1. ZIP을 `data-guard-agent` 폴더 **밖에 독립적으로 압축 해제**합니다. ZIP 내부 파일을 한 폴더에 모두 둡니다.
2. Ollama가 설치되고 `qwen2.5:7b-instruct` 모델이 있는지 확인합니다.
3. `RUN_CASE_RAG.cmd`를 더블클릭합니다. PowerShell에서도 다음과 같이 실행할 수 있습니다.

```powershell
Set-Location "C:\Users\USER\Desktop\최가윤\DataGuard_CaseRAG_Lab_v01"
python .\case_rag_ui.py
```

예시는 압축 해제 위치에 맞춰 경로를 바꿔야 합니다. Gradio가 설치되지 않았다면 사내 정책을 확인한 다음 해당 Python 환경에 `python -m pip install gradio`로 설치합니다.

4. 브라우저에서 `http://127.0.0.1:7862`가 열립니다. 기존 DataGuard와 다른 포트를 사용합니다.
5. `① Case RAG 전후 성능 비교` 탭에서 `로컬 Ollama 모델 확인`을 누릅니다.
6. **S02**를 선택하고 `가상 데모 유사 사례로 검색 실험`을 체크한 상태로 `현재 사례로 A/B 로컬 Ollama 실행`을 누릅니다. 두 번의 Ollama 실제 호출이 진행됩니다.
7. **A와 B가 각각 쓴 한국어 '보완 후' 제안**과 검색 사례를 비교합니다. Ground Truth는 모델 프롬프트에 **전달되지 않습니다.**
8. 담당자 평가에서 A/B 각각 `적절 / 부적절 / 추가 검토 필요`와 근거를 저장합니다. 결과 CSV·Excel을 다운로드할 수 있습니다.

## 왜 실사례 RAG 모드에서 처음에 B가 비어 있나?

기존 6건(S01~S06)은 가상 테스트에 대한 담당자 평가이므로, 실데이터와 승인된 사업별 규칙을 대조한 **RAG 승인 사례는 0건**입니다. 프로그램은 이 여섯 건을 **자동 승인하지 않습니다.**

- **가상 데모 모드**: 별도 가상 사례 `DEMO-TOPLEVEL-KEY`를 검색합니다. S02와 다른 경로(`$.note`)를 사용하므로, S02의 모범답안 자체를 넣지는 않습니다. 검색·전달 흐름을 설명하기 위한 실험이며 업무 근거는 아닙니다.
- **승인된 실사례만 모드**: `② 실제 승인 사례 등록`에서 담당자가 증빙을 확인한 사례만 검색합니다. 승인 사례가 없으면 B 모델 호출을 생략하고 그 이유를 기록합니다.

## 019번 실제 사례를 등록하는 방법 (권장 후속 실험)

019번 검사결과서의 **최상위 미정의 `text` 키**와 **`shapes[*].text` 허용·필수** 규칙이 다르다는 내용을 근거로, 다음 순서대로 확인합니다.

1. 해당 검사의 실제 라벨링 JSON 원본을 **로컬에서** 열어 최상위 `$.text`가 있는지 확인합니다. 배열 내부 `$.shapes[*].text`와 혼동하지 않습니다.
2. 검사결과서에서 이 오류의 정확한 **사업 ID / 파일명 / 오류 유형 / 경로 / 규칙 시트·행**을 확인합니다.
3. 승인된 보완결과서에서 적절한 `보완 후` 문장과 검토자의 최종 승인 기록을 확인합니다.
4. `② 실제 승인 사례 등록`에 이 내용을 입력하고 **실제 파일 대조·규칙 대조·담당자 승인**을 모두 확인한 경우에만 세 가지 체크박스를 선택하고 등록합니다.
5. `① Case RAG 전후 성능 비교`의 **가상 데모 체크를 해제**하고 S02와 같은 구조의 새로운 검증용 사례를 A/B 비교합니다. 단, 동일 평가 사례를 그대로 승인 KB에 넣어 재시험하면 정답 누출로 평가가 왜곡됩니다.

**주의:** 승인 등록 화면의 3가지 체크는 **담당자가 검증했다는 진술**입니다. 이 프로그램이 실제 JSON 원본이나 사업별 Excel 규칙을 자동으로 읽고 검증하는 기능은 아직 아닙니다. 파일이 없으면 삭제 완료로 단정하지 않습니다.

| `lab_data/results/` | 실제 모델 실행 및 담당자 평가 CSV/XLSX 기록 |

## 검증 방법

```powershell
python -m unittest -v test_case_rag.py
```

파이썬 단위 테스트는 **모의 Ollama 응답**으로 KB 검색·비노출·차단 조건을 검증합니다. 실제 Qwen2.5 7B가 더 정확해지는지 여부는 **본인 PC에서 A/B를 실행하고 판단**해야 하며, 개선이 보장되는 것은 아닙니다.

## 보안 및 제약

- 실데이터·회사 검사결과서를 외부 LLM API로 보내지 않습니다. 호출 주소는 `http://127.0.0.1:11434`로 고정합니다.
- 원본 JSON/TXT/CSV, 검사결과서 Excel, 사업 규칙 파일을 직접 읽거나 수정하지 않습니다. 현재 실험은 **CSV로 구성된 오류 사례 텍스트**만 사용합니다.
- 기존 DataGuard 본체의 Correction Agent도 그대로 유지합니다. 본 실험에서 검증된 방식만 이후 통합합니다.
- 실제 데이터 경로, 승인 사례, 실행 결과는 회사 허가 없이 공개 GitHub/클라우드에 올리지 않습니다.
- 동일한 모범답안을 Case KB에 넣은 뒤 같은 테스트 문제로 평가하면 **데이터 누출**입니다. 실험용 Ground Truth와 승인 KB는 분리해야 합니다.
